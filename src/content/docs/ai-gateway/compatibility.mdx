"OpenAI-compatible" is a claim about a surface, not a promise about all of it.
This page states the boundary. An exclusion you discover at runtime instead of
reading it here is a documentation bug. If you hit one, report it.

Everything below was checked against the live gateway at
`https://ai.varity.app/v1`, its canonical host, and against the contract it
publishes at `GET /v1/openapi.json`. `https://varity.app/v1` is a compatibility
alias routed to the same service and serves the same surface.

## Endpoints

| Endpoint | Status |
|----------|--------|
| `POST /v1/chat/completions` | **Supported.** Requires a bearer API key. Streaming and tool-call generation on eligible models. |
| `GET /v1/models` | **Supported.** Public, no key required. |
| `POST /v1/embeddings` | **Supported.** Requires a bearer API key. Only a model whose `capabilities.output_modalities` includes `embedding` is routable. |
| `POST /v1/images/generations` | **Supported.** Requires a bearer API key. Image-capable models only; results are returned inline as base64 and never stored. |
| `POST /v1/images/edits` | **Supported.** Requires a bearer API key. JSON with base64 image data (`image/png`, `image/jpeg`, `image/webp`); a source image or mask at or above 25 MB is rejected. |
| `POST /v1/audio/transcriptions` | **Supported.** Requires a bearer API key. JSON with the audio as a base64 typed part; the model must advertise `capabilities.transcription`. Returns JSON, or plain text when `response_format` is `text`. No streaming mode. |
| `POST /v1/audio/speech` | **Supported.** Requires a bearer API key. The model must advertise `capabilities.speech` and the format must be one of its `capabilities.speech_formats`. Returns audio bytes with a matching `audio/*` content type; `stream: true` gives a chunked binary response, not SSE. |
| `GET /v1/models/{id}` | **Not implemented.** Returns `404`. Fetch the list and filter client-side. |
| `POST /v1/completions` (legacy text completions) | **Not implemented.** Returns `404`. |
| `POST /v1/responses` | **Not implemented.** Returns `404`. |
| `/v1/assistants` | **Not implemented.** Returns `404`. |
| `/v1/files` | **Not implemented.** Returns `404`. |
| `/v1/vector_stores` | **Not implemented.** Returns `404`. |
| `POST /v1/moderations` | **Not implemented.** Returns `404`. |
| `/v1/batches` | **Not implemented.** Returns `404`. |
| `/v1/fine_tuning/jobs` | **Not implemented.** Returns `404`. |

Beyond the OpenAI surface, the gateway serves its own endpoints. These have no
OpenAI equivalent, so a client written against the OpenAI spec will not find
them, but they are public and stable.

| Endpoint | Status |
|----------|--------|
| `GET /v1/openapi.json` | **Supported.** Public, no key required. The machine-readable contract for this surface, including the data-handling block below. |
| `GET /v1/inference/requests` | **Supported.** Requires a bearer API key. Per-request metadata. `created_after` and `created_before` take RFC 3339 timestamps; send them with fractional seconds, for example `2026-09-16T00:00:00.000Z`. |
| `GET /v1/inference/usage` | **Supported.** Requires a bearer API key. |
| `GET /v1/inference/policy` | **Supported.** Requires a bearer API key. Returns the privacy floor (`private` or `anonymized`) enforced for the account, and the account's `requests_per_minute`, `concurrency_limit` and `limits_scope`; with a scoped key the key's effective floor and its own limit overrides are reported beside them. |
| `GET /v1/inference/performance` | **Supported.** Requires a bearer API key. Accepts `window` of `1h`, `24h`, `7d`, or `30d`. |

### Account routes

The AI Gateway host also serves the account routes for its own keys, prepaid
balance, and privacy entitlement. These require a Developer Portal session token
as the bearer credential; an inference API key is refused on them.

| Endpoint | Status |
|----------|--------|
| `GET /v1/keys` | **Supported.** Secret-free list of the account's inference keys. |
| `POST /v1/keys` | **Supported.** Mints an inference-only key; the plaintext is returned exactly once. |
| `GET /v1/keys/audit` | **Supported.** Secret-free key lifecycle events. Accepts `limit`. |
| `POST /v1/keys/{id}/revoke` | **Supported.** Revokes one of the account's own keys. |
| `PUT /v1/inference/policy` | **Supported.** Sets the account's privacy floor to `private` or `anonymized`. `anonymized` is the default for an account that never chose; choosing `anonymized` requires `acknowledge_anonymized_processing: true`. |
| `GET /v1/billing/balance` | **Supported.** The prepaid Gateway balance. |
| `GET /v1/billing/transactions` | **Supported.** Balance transactions. Accepts `limit` and `offset`. |
| `PATCH /v1/billing/settings` | **Supported.** Monthly spending limit and auto-reload. |
| `POST /v1/billing/top-up` | **Supported.** Starts a card checkout using the funding terms in the live OpenAPI commercial-contract block. See [Billing and Keys](/ai-gateway/billing-and-keys/). |

The same keys can also be created from the platform API with
`POST /api/api-keys/inference`; see the
[Public API Reference](/ai-tools/api-reference/).

Hosted tool execution, batch, files, assistants, fine-tuning, and moderation
are not part of the surface. Unimplemented routes return `404` with the JSON
error envelope below (`code: "invalid_request"`, message `Route not found.`).
Branch on the HTTP status code, not on the message text.

Unauthenticated health and readiness probes are available outside `/v1` on the
canonical host:

| Endpoint | Status |
|----------|--------|
| `GET /healthz` | **Supported.** Public. Returns `{"status":"ok","service":"varity-ai-gateway","version":"<deployed build>","source_commit":"<commit>"}` (re-probe for the current build rather than pinning it). |
| `GET /readyz` | **Supported.** Public. Same fields plus `servable`, `published`, and `minimum_servable` model counts. |

<Aside type="caution">
Any OpenAI SDK helper that touches an unimplemented route will fail, including
the Assistants and Responses APIs, file upload helpers, and batch. The
`chat.completions`, `models`, `embeddings`, `images.generate`, and
`audio.speech` namespaces work unchanged, on the models whose `capabilities`
advertise them. `images.edit` and `audio.transcriptions` need a different call
shape — see below.
</Aside>

## The Two SDK Exceptions

"Point your OpenAI client at the base URL and change nothing else" is true for
every route except two. `images.edit` and `audio.transcriptions` are the
operations the OpenAI SDKs send as `multipart/form-data`, and these routes
accept `application/json` only. A multipart request is refused with `415`:

```json
{
  "error": {
    "message": "This endpoint accepts application/json only: send the audio as audio.data (base64) with audio.media_type. multipart/form-data is not accepted.",
    "type": "invalid_request_error",
    "code": "invalid_request",
    "param": null,
    "retryable": false,
    "request_id": "…"
  }
}
```

The refusal names the JSON shape rather than blaming a field you did send. Call
these two with a plain HTTP client and inline base64:

```bash
curl https://ai.varity.app/v1/images/edits \
  -H "Authorization: Bearer $VARITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<an image-capable model id>",
    "prompt": "Make the sky orange.",
    "image": { "data": "<base64 bytes>", "mime_type": "image/png" }
  }'
```

`image.mime_type` is one of `image/png`, `image/jpeg`, or `image/webp`. An
optional `mask` takes the same `{ data, mime_type }` shape, and `size` is
optional.

```bash
curl https://ai.varity.app/v1/audio/transcriptions \
  -H "Authorization: Bearer $VARITY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<a transcription model id>",
    "audio": { "data": "<base64 bytes>", "media_type": "audio/mpeg" }
  }'
```

`audio.media_type` is one of `audio/wav`, `audio/wave`, `audio/x-wav`,
`audio/flac`, `audio/x-flac`, `audio/mp4`, `audio/m4a`, `audio/x-m4a`,
`audio/aac`, `audio/mpeg`, `audio/ogg`, `audio/oga`, or `audio/webm`. Optional
fields are `audio.filename`, `response_format` (`json` or `text`), `language`,
and `timestamps`. Decoded audio must be under 25 MB.

Both shapes are on `GET /v1/openapi.json`, so you can generate a client from
the contract rather than transcribing this page.

## Per-Model Capabilities

Compatibility is not uniform across models. Each catalog entry carries a
`capabilities` object, and you must read it. The same request that works
against one model can be unsupported on another.

| Capability | Models supporting it |
|------------|----------------------|
| `chat_completions` | The chat models; image, audio, and embedding models report `false` |
| `streaming` | Chat models reporting `streaming: true` |
| `tool_calls` | Chat models reporting `tool_calls: true` |
| `streaming_tool_calls` | Chat models reporting `streaming_tool_calls: true` |
| `output_modalities` | `text`, `embedding`, `image`, or `audio`: the route a model belongs on |
| `transcription`, `speech` | The audio models, each on exactly one of the two audio routes |

### Check tool calling per model

Most chat models accept `tools` / `tool_choice`, but not all: a model reporting
`tool_calls: false` rejects them. Resolve this at runtime rather than hardcoding
a list:

```python
models = {m["id"]: m for m in client.models.list().model_dump()["data"]}

def supports_tools(model_id, streaming=False):
    caps = models[model_id]["capabilities"]
    return caps["streaming_tool_calls"] if streaming else caps["tool_calls"]
```

<Aside type="note">
The OpenAI Python SDK exposes only the fields it knows about on typed objects.
Varity's extra fields (`capabilities`, `context_window`, `customer_pricing`)
arrive as extra JSON, so read the raw dict (or call `/v1/models` directly with an
HTTP client) rather than expecting SDK attributes for them.
</Aside>

## Model Identifiers

Varity model ids are **not** guaranteed to be OpenAI model ids. Some entries now
carry OpenAI-style names such as `gpt-4o`, but every id is a Varity catalog entry
with Varity routing and pricing, and there is no aliasing layer that maps an
OpenAI name onto a different model. A request naming an id that is not in the
live catalog is a request for a model that does not exist here.

Ids are readable human slugs, for example `glm-5-1`, `glm-5-2`,
`llama-3-3-70b`, and `qwen-3-5-35b-a3b`. Always take ids from
[the live catalog](/ai-gateway/models/).

## Limits That Differ From OpenAI

- **`max_completion_tokens` is per-model and often small.** The ceiling is independent of the context window, so a very large context does not mean a long reply is allowed. Read both fields per model.
- **Cached-input pricing is per model.** Some models price `cached_input` below `input` and others price them the same. Read `customer_pricing.cached_input` per model.
- **There is a concurrency bound as well as a rate limit.** Inference is held to 120 requests per minute *and* 4 in-flight requests, both counted for the whole account rather than per key. `GET /v1/inference/policy` publishes your own numbers. See [Rate Limits](/ai-gateway/limits/).
- **`GET /v1/models` carries no request budget** and returns no `RateLimit-*` headers. The headers live on the inference and inference-read routes, not on catalog discovery.

## Errors

The error envelope matches OpenAI's shape and adds two fields:

```json
{
  "error": {
    "message": "The provided credential is invalid or expired.",
    "type": "authentication_error",
    "code": "authentication_required",
    "param": null,
    "retryable": false,
    "request_id": "504f4a24-1427-4483-89fe-ad332fdad5d6"
  }
}
```

- `retryable` is a boolean OpenAI does not send. Use it instead of guessing from the status code whether to retry.
- `request_id` is also returned as the `x-request-id` response header on every response, successful or not. A caller-supplied `x-request-id` that is a canonical UUID is echoed back as the request id; any other value is replaced by a UUID the gateway generates.

A managed-inference failure adds a diagnostic block naming who decided the
failure and where in the request's life it happened:

| Field | Meaning |
|-------|---------|
| `diagnostic_code` | `ai_gateway.<code>`. |
| `failure_cause` | The same value as `code`. |
| `failure_domain` | `varity_projection` (Varity refused), `supplier_observed` (a model provider answered and Varity observed it), or `dependency_observed` (a Varity-operated dependency was unreachable, named in `dependency`). |
| `lifecycle_stage` | `admission`, `provider_attempt`, `settlement`, or `terminal`. |
| `action` | What to do next, in one sentence. |

### Error Codes

Branch on `code`. `error.retryable` is on every body and is authoritative for
that response; the column below is what the gateway publishes today.

**Varity refused the request** (`failure_domain: "varity_projection"`):

| Code | HTTP | Retryable | Cause |
|------|------|-----------|-------|
| `authentication_required` | `401` | no | No bearer credential, or one that is invalid, revoked, or expired. |
| `invalid_request` | `400` | no | The body failed validation. Also `404` on an unimplemented route, `413` when the body exceeds the route ceiling, and `415` on `multipart/form-data`. |
| `input_modality_unsupported` | `400` | no | Every route for this model rejected the supplied image or document part. Distinct from `invalid_request` so you can tell "this model cannot see" from "this body is malformed". |
| `model_not_found` | `404` | no | The id is not in the live catalog. |
| `model_not_allowed` | `403` | no | The model exists but this credential's model scope excludes it. |
| `tenant_not_admitted` | `403` | no | Managed inference is not enabled for the account, or the key is expired. |
| `privacy_policy_violation` | `403` | no | The request asked for a privacy floor weaker than the account's. |
| `duplicate_request` | `409` | no | The idempotency identity was already admitted. |
| `request_cancelled` | `408` | no | The deadline elapsed, or the caller closed the socket. |
| `rate_limit_exceeded` | `429` | yes | The account's requests-per-minute budget is exhausted. See [Rate Limits](/ai-gateway/limits/). |
| `concurrency_limit_exceeded` | `429` | yes | The account's in-flight bound is exhausted. |
| `budget_exceeded` | `429` | yes | The account's inference budget for the period is exhausted. |
| `payment_method_required` | `402` | no | No active payment method. |
| `insufficient_gateway_balance` | `402` | no | The prepaid AI Gateway balance cannot cover the request. |
| `gateway_balance_frozen` | `402` | no | The balance is frozen pending billing review. |
| `billing_unavailable` | `503` | yes | The isolated billing ledger could not answer. Not your request's fault. |
| `internal_error` | `500` | no | An unclassified gateway failure. Quote `request_id`. |

**A model provider decided it** (`failure_domain: "supplier_observed"`):

| Code | HTTP | Retryable | Cause |
|------|------|-----------|-------|
| `model_unavailable` | `503` | yes | No callable route for this model right now. Choose another model or retry. |
| `privacy_route_unavailable` | `403` | no | The model has no callable route at the required privacy level. |
| `upstream_rate_limited` | `429` | yes | The provider is rate-limiting. Carries `Retry-After` only when the provider published its own reset. |
| `upstream_unavailable` | `503` | yes | No qualified route answered. |
| `upstream_balance_exhausted` | varies | no | Provider funding is exhausted. Varity's problem, not yours; pick another model. |
| `upstream_timeout` | varies | yes | The provider did not answer in time. Retry only if the request is known not to have taken effect. |
| `stream_terminated` | — | no | A stream ended mid-flight. Do not replay an ambiguously chargeable stream; inspect the correlated request instead. |

<Aside type="note">
`upstream_authentication_failed` exists in the gateway's internal vocabulary but
never reaches you. A refused Varity provider credential is something only Varity
can fix, so it is published as `model_unavailable` — the one thing a caller can
act on — and the real cause stays in the operator record.
</Aside>

Authentication is evaluated **before** request-body validation, so an
unauthenticated request with an invalid `model` returns the authentication
error, not a model error. Do not use the error type to infer that your payload
was accepted.

<Aside type="caution">
These codes are the AI Gateway's own. The platform API at `varity.app/api` uses
a **different envelope and a different code vocabulary** — see
[API Errors](/api/errors/). In particular the AI Gateway never emits
`invalid_api_key`; an invalid key here is `authentication_required`.
</Aside>

## Privacy And Data Retention

The gateway publishes its data-handling contract as an `x-varity-data-handling`
block at the root of `GET /v1/openapi.json`. It is machine-readable, so you can
assert against it in CI rather than taking a page's word for it.

| Field | Value |
|-------|-------|
| `inference_metadata_retention_days` | `30` |
| `stored_content` | `[]` |
| `content_never_stored` | `prompts`, `responses`, `tool_arguments`, `uploaded_content`, `generated_image_bytes`, `playground_conversations` |
| `generated_image_retention` | `inline_only` |
| `financial_and_security_records` | `separate_retention_classes` |

Prompt, response, uploaded, and generated-image bytes are never written to the
inference records. What is retained for 30 days is request metadata: model id,
token counts, latency, fallback count, error code, and timestamps. Read it back
with `GET /v1/inference/requests`.

This is the property usually searched for as zero data retention, or ZDR.

## Privacy Routing

The live catalog reports two routing privacy classes: `privacy: "private"` with
`privacy_routes: ["private"]`, and `privacy: "anonymized"` with
`privacy_routes: ["anonymized"]`. This field has no OpenAI equivalent; it is
Varity-specific catalog metadata describing how each model is routed. Read it per
model.

Your account has a privacy floor. It is `anonymized` unless you choose
otherwise, which lets requests use both `private` and `anonymized` models. Set it
to `private` with `PUT /v1/inference/policy` (or on the portal's **Gateway
settings** tab) and only `private` models are callable. A single chat request can
tighten the floor, never loosen it, with
`"varity_extensions": { "privacy_floor": "private" }`; asking for a weaker floor
than the account's returns `403 privacy_policy_violation`.
