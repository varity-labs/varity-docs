The Varity AI Gateway is an OpenAI-compatible inference API. It speaks the same
chat-completions wire format as the OpenAI API, so every OpenAI SDK, framework
adapter, and agent runtime already knows how to talk to it. For chat,
streaming, tool calls, embeddings, image generation, and speech, the
integration is a one-line base-URL swap.

Two SDK calls are **not** covered by that swap, because they send
`multipart/form-data` and these routes take JSON: `images.edit` and
`audio.transcriptions` both answer `415`. Send the bytes as base64 in the JSON
body instead — the working shapes are in
[Compatibility](/ai-gateway/compatibility/#the-two-sdk-exceptions).

```text
https://ai.varity.app/v1
```

`https://ai.varity.app` is the canonical AI Gateway host. `https://varity.app/v1`
remains a compatibility alias that the edge routes to the same service, so
existing clients keep working; new integrations should use `ai.varity.app`.

Chat completions are the core, and the same host serves OpenAI-compatible
[embeddings, image generation and editing, transcription, and
speech](/ai-gateway/compatibility/) on the models whose `capabilities` advertise
them.

## Fastest Path

Set two variables and send a request. This is the whole integration.

<Tabs>
  <TabItem label="curl">

    ```bash
    curl https://ai.varity.app/v1/chat/completions \
      -H "Authorization: Bearer $VARITY_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "model": "glm-5-2",
        "messages": [
          { "role": "user", "content": "Say hello in one sentence." }
        ]
      }'
    ```

  </TabItem>
  <TabItem label="Python">

    ```python
    # pip install openai
    import os
    from openai import OpenAI

    client = OpenAI(
        base_url="https://ai.varity.app/v1",
        api_key=os.environ["VARITY_API_KEY"],
    )

    response = client.chat.completions.create(
        model="glm-5-2",
        messages=[{"role": "user", "content": "Say hello in one sentence."}],
    )

    print(response.choices[0].message.content)
    ```

  </TabItem>
  <TabItem label="Node">

    ```javascript
    // npm install openai
    import OpenAI from "openai";

    const client = new OpenAI({
      baseURL: "https://ai.varity.app/v1",
      apiKey: process.env.VARITY_API_KEY,
    });

    const response = await client.chat.completions.create({
      model: "glm-5-2",
      messages: [{ role: "user", content: "Say hello in one sentence." }],
    });

    console.log(response.choices[0].message.content);
    ```

  </TabItem>
</Tabs>

`base_url` / `baseURL` is the only line that differs from an OpenAI setup. Model
ids come from the Varity catalog, not OpenAI's. See
[Models](/ai-gateway/models/) for the full list.

The gateway also exposes unauthenticated health and readiness probes on the
canonical host:

```bash
curl https://ai.varity.app/healthz
curl https://ai.varity.app/readyz
```


`/readyz` adds `servable` and `published` model counts. The `version` field
reports the deployed gateway build; re-probe for the current one rather than
pinning it in your own config.

## Authentication

Inference requests require a Varity API key sent as a bearer credential:

```text
Authorization: Bearer $VARITY_API_KEY
```

Create keys on the Developer Portal's [AI Gateway page](https://developer.store.varity.so/dashboard/ai-gateway?utm_source=docs&utm_medium=content&utm_campaign=docs-to-portal&utm_content=ai-gateway-api-keys), under the
**Inference keys** tab. Key plaintext is shown once
at creation and is never returned again; the list identifies each key by its
key id (`vki_…`). The same key format is used across the
Varity [public API](/ai-tools/api-reference/).

Auth is enforced on every inference route. A request with no `Authorization`
header returns `401`:

```json
{
  "error": {
    "message": "A bearer credential is required.",
    "type": "authentication_error",
    "code": "authentication_required",
    "param": null,
    "retryable": false,
    "request_id": "516c24ef-ba5a-4e3d-8f32-0a609ae5d298"
  }
}
```

A malformed, revoked, or expired key also returns `401` with
`code: "authentication_required"`; only the message differs:
`The provided credential is invalid or expired.` Treat any `401` as "send a
valid key" rather than branching on the message text.

<Aside type="note">
Authentication is checked before the request body is validated. An unauthenticated
request naming a nonexistent model still returns the authentication error, not a
model error.
</Aside>

## Streaming

Set `stream: true` for server-sent events, exactly as with OpenAI. Most, but not
all, models in the catalog support streaming, so read `capabilities.streaming`
per model rather than assuming it is universal.

<Tabs>
  <TabItem label="curl">

    ```bash
    curl https://ai.varity.app/v1/chat/completions \
      -H "Authorization: Bearer $VARITY_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "model": "glm-5-2",
        "stream": true,
        "messages": [
          { "role": "user", "content": "Count to five." }
        ]
      }'
    ```

  </TabItem>
  <TabItem label="Python">

    ```python
    stream = client.chat.completions.create(
        model="glm-5-2",
        messages=[{"role": "user", "content": "Count to five."}],
        stream=True,
    )

    for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:
            print(delta, end="")
    ```

  </TabItem>
  <TabItem label="Node">

    ```javascript
    const stream = await client.chat.completions.create({
      model: "glm-5-2",
      messages: [{ role: "user", content: "Count to five." }],
      stream: true,
    });

    for await (const chunk of stream) {
      process.stdout.write(chunk.choices[0]?.delta?.content ?? "");
    }
    ```

  </TabItem>
</Tabs>

Streaming *tool calls* are a narrower capability than streaming text, and are
only supported on some models. Check `capabilities.streaming_tool_calls` before
you combine `stream: true` with `tools`. See
[Compatibility](/ai-gateway/compatibility/).

## Errors

Errors use the OpenAI error envelope, with two Varity additions: `retryable` and
`request_id`.

| Field | Meaning |
|-------|---------|
| `error.message` | Human-readable description |
| `error.type` | Error class, for example `authentication_error` |
| `error.code` | Stable machine code, for example `authentication_required` |
| `error.param` | Offending request field, or `null` |
| `error.retryable` | Whether retrying the same request can succeed |
| `error.request_id` | Correlation id, also returned as the `x-request-id` response header |

Quote `request_id` in any support request. It is present on both the response
body and the `x-request-id` header on every response, including successful ones.
The gateway generates it; a caller-supplied `x-request-id` header is not echoed.

## Rate Limits

Inference is bounded two ways at once: **120 requests per minute** and **4
concurrent requests**, both counted across your whole account rather than per
key. Crossing either returns `429`, before any model provider is called.

Read your own numbers instead of hardcoding these defaults:

```bash
curl https://ai.varity.app/v1/inference/policy \
  -H "Authorization: Bearer $VARITY_API_KEY"
```

```json
{
  "object": "inference.tenant_policy",
  "privacy_floor": "private",
  "requests_per_minute": 120,
  "concurrency_limit": 4,
  "limits_scope": "account"
}
```

`GET /v1/models` is public and carries no request budget at all. The budgets,
the exact headers each refusal returns, and the body-size ceilings are on
[AI Gateway Rate Limits](/ai-gateway/limits/).
