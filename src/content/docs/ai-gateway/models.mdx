The catalog is served live. This page is a snapshot of it; the endpoint is the
source of truth:

```bash
curl https://ai.varity.app/v1/models
```

`GET /v1/models` is public and needs no API key. It returns an OpenAI-shaped
`{ "object": "list", "data": [...] }` response plus a top-level
`privacy_scope`, the privacy floor the public catalog is projected at
(`"anonymized"` on this unauthenticated route). Varity adds fields OpenAI does
not return on each entry: `display_name`, `maker`, `capabilities`,
`context_window`, `max_completion_tokens`, `privacy`, `privacy_routes`,
`availability`, `refreshed_at`, and `customer_pricing`.

<Aside type="tip" icon="approve-check">
Do not hardcode the catalog. Resolve models at runtime from `/v1/models` and read
`capabilities` per model. The catalog changes without a docs release.
</Aside>

## Catalog

The catalog is not chat-only. Each entry's `capabilities.output_modalities`
says what the model produces: `text` (chat completions), `embedding`, `image`,
or `audio` (speech). Transcription models take `audio` in and return `text`.
The live catalog currently reports `availability.status: "available"` on every
entry, but that is not a promise: read it per model from the endpoint rather
than from this page.

Pass an entry's `id` verbatim as the `model` field of a request on the matching
route. Ids are readable human slugs, for example `glm-5-2`, `llama-3-3-70b`, and
`gpt-4o`. `display_name` is a separate human label, not an identifier.

`maker` says who built the model, never who serves it (`owned_by` is always
`varity`). It carries a stable slug `key` and a human `label`; the key is
`unreported`, with the label `Maker not published`, when no maker evidence was
observed.

Prices are USD, taken from each model's `customer_pricing` object, and the
`unit` differs by modality: see [Pricing](#pricing) below.

This page carries no model table on purpose. A snapshot of ids, context windows,
capabilities, and prices is stale the moment the catalog changes, so query
`GET /v1/models` and read the fields below instead.

## Reading The Catalog Fields

Each entry in `data` carries these Varity fields:

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Pass this as `model` in a request |
| `display_name` | string | Human label only, never an identifier |
| `maker.key` | string | Stable slug of who built the model, for example `zai`; `unreported` when unknown |
| `maker.label` | string | Human maker label, for example `Z.ai` |
| `capabilities.input_modalities` | array | What a request may carry: `text`, `image`, `audio`, `video`. `document` input is not currently routed: no model advertises it, and a `document` content part is rejected with `400 input_modality_unsupported` |
| `capabilities.output_modalities` | array | What the model produces: `text`, `embedding`, `image`, `audio` |
| `capabilities.chat_completions` | boolean | `true` on the chat models only; image, audio, and embedding models report `false`. Read it per model |
| `capabilities.tool_calls` | boolean | Supported on a subset of the catalog; read it per model |
| `capabilities.streaming` | boolean | Supported on most, not all, chat models; read it per model |
| `capabilities.streaming_tool_calls` | boolean | Narrower than `streaming`; read it per model. Absent on a few entries, which means unproven, not unsupported |
| `capabilities.transcription` | boolean | `true` when `POST /v1/audio/transcriptions` accepts the model |
| `capabilities.speech` | boolean | `true` when `POST /v1/audio/speech` accepts the model; `speech_formats` lists its output formats |
| `context_window` | integer | Total tokens, input plus output |
| `max_completion_tokens` | integer | Ceiling on generated tokens |
| `privacy` | string | Routing privacy class. The live catalog contains both `"private"` and `"anonymized"` entries |
| `privacy_routes` | array | Route set matching `privacy` |
| `availability.status` | string | `"available"` on every model, with an `observed_at` timestamp |
| `customer_pricing` | object | See below |
| `refreshed_at` | string | When the gateway last refreshed the entry |

### Pricing

Every model in the current catalog returns `customer_pricing.status: "configured"`
with concrete numbers. The schema also allows `status: "not_configured"`, which
carries no other fields, so branch on `status` before reading a rate:

```json
"customer_pricing": {
  "status": "configured",
  "version": "2026-07-28.v3.d74e3f5155b10314",
  "observed_at": "2026-08-01T02:30:58.677Z",
  "currency": "usd",
  "unit": "per_million_tokens",
  "input": 1.47,
  "output": 4.62,
  "cached_input": 1.47
}
```

`currency` is always `usd`. `unit` takes one of four values, and it decides
which fields carry the rate:

| `unit` | Models | Where the rate is |
|--------|--------|-------------------|
| `per_million_tokens` | Chat and embedding models | `input` and `output` per million tokens; `cached_input` for cached prompt tokens |
| `per_image` | Image generation and editing models | `request`, a flat price per generated image; `input`, `output`, and `cached_input` are `0` |
| `per_million_characters` | Speech models | `input` per million characters of text; `output` and `cached_input` are `0` |
| `per_audio_second` | Transcription models | `input` per second of audio; `output` and `cached_input` are `0` |

`request` is present only on `per_image` entries. `cached_input` equals
`input` on every token-priced model in the current catalog, so cached input
tokens are not discounted today. Always read `unit` and `currency` rather than
assuming; the `version` string identifies the immutable price set the numbers
came from and `observed_at` says when the gateway last observed it. Rates are
the current managed rate for the model's preferred route, not a permanent
guarantee: each admitted request snapshots its own price before it runs.

Input and output prices both vary widely across the catalog and change with it,
so read `customer_pricing` per model instead of carrying a range from this page.

### Context Windows

Context windows vary per model, and `max_completion_tokens` is a separate, much
smaller ceiling on any single response. A large context window does not imply a
large answer, so read both fields per model.

## Picking A Model

- **Need tool calling?** Only a subset of the catalog accepts `tools` / `tool_choice`, and fewer support them while streaming. Read `capabilities.tool_calls` and `capabilities.streaming_tool_calls` per model, and see [Compatibility](/ai-gateway/compatibility/).
- **Need a very large context?** Sort the live catalog by `context_window`. The Grok 4.20 entries (`grok-4-20`, `grok-4-20-multi-agent`) have the widest windows in the current catalog, but read the field rather than assuming.
- **Cost sensitive?** Compare `customer_pricing.input` across the live catalog, within one `unit`. Embedding models carry the lowest token rates; among chat models, `mercury-2-5` and `glm-4-7-flash` have the lowest input rates in the current catalog.

<Aside type="caution">
There is no per-model retrieval route. `GET /v1/models/{id}` returns `404`; fetch
the list and filter it client-side.
</Aside>
